# 学长组 Agent：项目 TODO 与任务分配

更新日期：2026-08-03

## 1. 当前基础

- 已治理 134 篇知识文档；向量索引需在发布前按新元数据重建。
- 已实现增量入库、向量 + BM25 混合召回、RRF、重排、多轮改写、引用和基础拒答。
- 已实现 Streamlit 问答、登录、用户管理、学长笔记和 FAQ 导出。
- 已有 Docker、Compose、Linux 部署说明基础说明。
- 当前检索回归集为 27 条正例、4 条负例；实测 hit@5 为 96%，MRR 为 0.811（———gpt）。

下一阶段重点：**数据可信、持续更新、拒答安全、产品引导、真实评测和稳定上线**。

## 2. 现状问题与初步解决思路

| 问题 | 当前表现 | 初步解决思路 |
|---|---|---|
| 来源可信度未分层 | 治理后 134 篇中有 94 篇为学生资料；元数据已区分，但界面尚未明显展示 | 应用层读取 `source_type`、`authority_level`，检索优先官方来源，学生资料明确标注“仅供参考” |
| 入库校验偏弱 | schema v2 已拦截字段、日期、占位链接和状态冲突；仍有 6 个首页链接待修复 | 在现有质量门禁上补链接可达性检查，并将审计加入发布流程 |
| 时效与适用范围不足 | 新字段已迁移，但大部分旧文档仍为 `needs_review`，未知范围未完成人工补全 | 按负责人逐批核验有效期、适用人群、校区、学院、替代文件和核验时间 |
| 知识库更新链路只有后半段 | 已支持 hash 增量入库，但缺少来源登记、定时抓取、差异审核和自动发布；更新后 BM25 还需重启 | 建立“来源注册→API/爬虫→差异→审核→发布→自动刷新→回滚”流水线 |
| Skill 不适合直接维护正式库 | Agent 爬取灵活，但网页变化和判断错误可能污染知识库。以及agent成本可能比较难以估算 | API/固定爬虫作为主干；Skill 负责发现和异常解析；高风险变更人工审核 |
| 检索命中不等于可以回答 | 真实评测 hit@5 为 96%，但 4 个库外负例中有 3 个超过检索阈值 | 增加可回答性判断和引用支持检查；相似但无答案时拒答，不只依赖分数阈值 |
| 评测覆盖不足 | 当前只有 27 条正例、4 条负例，主要评检索，不评最终答案 | 全员收集真实问题；补充追问、冲突、过期和库外样本；增加答案、引用、版本、链接评测 |
| 产品仍以聊天框为主 | 用户需要自己组织问题，回答多为自然语言，办事入口不够突出 | 增加任务入口、主动追问和办事卡片，直接给出条件、时间、步骤、链接和部门 |
| 缺少反馈闭环 | 对话和笔记主要保存在 session；没有稳定积累无答案、过期和差评问题 | 将问题和反馈脱敏落库，形成评测样本和知识补充队列 |
| 管理后台只管用户 | 暂时不能查看待审核知识、抓取失败、失效链接和高频无答案问题 | 增加内容运营后台和知识库健康报告 |
| 全库目录注入难扩展 | 每次问答都注入完整目录，当前约增加 5932 个字符，知识增长后会增加延迟和成本 | 只在枚举问题中注入相关目录，或为文档目录单独建立索引 |
| 线上稳定性仍需验证 | 依赖只有范围约束；模型冷启动依赖网络；备份、监控和回滚尚未完成演练 | 锁定依赖、预下载模型、隔离测试/生产、配置监控并实际演练恢复和回滚 |

总体原则：

- **算法先守住边界，不急于重写检索骨架。** 当前检索基础较好，优先解决数据、拒答和评测。
- **自动化负责发现变化，人负责确认高风险变化，系统负责记录版本和责任。**
- **先完成可信和稳定上线，再扩展别的**

## 4. 五人任务分配

| 人员 | 主责 | 主要交付物 | 复核人 |
|---|---|---|---|
| 1号 | 知识库治理 | 数据清理、元数据规范、来源分级、审核规则、健康报告 | 2号 |
| 2号 | 自动采集与更新 | 来源注册表、API/爬虫、差异检测、审核发布、索引刷新 | 5号 |
| 3号 | RAG 与评测 | 可回答性判断、拒答、真实评测集、端到端指标、回归测试 | 1号 |
| 4号 | 产品与运营 | 任务入口、主动追问、办事卡片、反馈落库、内容运营后台 | 3号 |
| 5号 | 部署与运维 | Docker、域名、HTTPS、SMTP、依赖锁定、监控、备份和回滚 | 2号 |

协作边界：

- 1号定义知识规则，2号按规则生产数据，4号负责在界面展示规则结果。
- 2号负责更新成功，5号负责更新任务在线上稳定运行。
- 3号提供上线质量门槛，5号在发布流程中执行该门槛。
- 每项主线至少有一名复核人，避免形成单点维护。

## 5. 真实问题收集

目标：**每人收集 30 条原始问题，共 150 条；去重后保留约 100～120 条。**

要求：

- 每人从至少 5～8 名真实同学处收集，保留原始口语表达，不由组员自行编满。
- 不记录姓名、学号、手机号、具体成绩等隐私信息。
- 允许约 20% 题目重合，用于保留同一问题的不同表达。

| 人员 | 重点方向 |
|---|---|
| 1号 | 学籍、转专业、奖学金、处分、毕业 |
| 2号 | 最新通知、截止时间、学院差异、申请流程 |
| 3号 | 黑话、追问、错误前提、库外问题 |
| 4号 | 新生生活、宿舍、食堂、交通、办事入口 |
| 5号 | 校园网、邮箱、校园卡、系统登录、信息化服务 |

每条记录至少包含：

- 原始问题及必要上下文
- 学生类型、学院、年级、校区（如适用）
- 期望行为：回答、给链接、追问或拒答
- 标准答案要点和正确官方来源
- 是否含隐私、收集人和复核人

交叉复核：1号→2号→3号→4号→5号→1号。3号负责将复核通过的问题纳入自动评测，不独自承担标准答案整理。

## 6. 建议排期

### 第一周：规范和环境

- 1号完成数据问题清单和新字段规范。
- 2号完成来源注册表和首个采集器。

### 第二周：打通闭环

- 完成“采集→差异→审核→入库→刷新”。
- 完成知识库第一轮清理、拒答评测、反馈落库和基础监控。
- 全员各累计收集 30 条问题并完成交叉复核。

### 第三周：联调上线

- 全量运行真实问题回归和人工验收。
- 完成备份恢复、故障降级和发布回滚演练。
- 小范围邀请同学试用，修复高频失败后再扩大推广。

## 7. 上线完成标准

- P0 项全部完成，无有效示例、假链接和已知重复知识。
- 官方与非官方来源可区分，关键回答可追溯到有效原文。
- 测试和生产环境隔离，HTTPS、SMTP、备份、监控和回滚可用。
- 至少 100 条真实问题通过自动回归与人工抽查。
- 库外问题能稳定拒答，需要身份条件的问题会主动追问。
- 知识更新有负责人、审核记录、失败告警和版本回滚。
